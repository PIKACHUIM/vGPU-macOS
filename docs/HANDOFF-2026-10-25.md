## 1. 需求（要做什么）

**一句话**：在 VMware Workstation 的 macOS 客户机里，自研一套 SVGA3D 驱动栈，
让 macOS 拿到完整可用的 GPU 加速（桌面合成 + 应用级 Metal/OpenGL/Vulkan/D3D）。

拆开说：

| 层 | 目标 | 现状 |
|---|---|---|
| 传输层 | IOFramebuffer kext 接管显示 + FIFO 所有权 + GB/DX 命令提交 | **已达成**（显示实时渲染） |
| 命令层 | SVGA3D / vGPU10 DX 命令被宿主真正执行（渲染出像素） | **卡在这里**（RTV 被拒） |
| 驱动插件层 | Metal 驱动 bundle（AIR→SPIR-V→后端） | 未开始（模板已调研） |
| 生态层 | GL-on-Metal / MoltenVK / DXMT 自动覆盖 | 未开始 |

关键判据：**CLEAR 一个 surface → READBACK 读回 → 颜色对得上**（`ROUND TRIP VERIFIED`）。
只有拿到这个，才说明宿主真的在渲染，而不是"接受了命令但什么都没做"。

## 3. 当前状态（2026-10-25 00:50）

**同一 boot 实测**（`kFbStage=2 / kGbStage=4 / kDxTest=1 / kCbDump=1`，headless，SSH 活）：

```
CB 引导     START_STOP_CONTEXT{1,0}        ACCEPTED
DC cmd 3    {idx 1}                        ACCEPTED
DEFINE_CONTEXT{cid 1}                      ACCEPTED
BIND_CONTEXT  {cid 1, mob 3, valid 0}      ACCEPTED
SET_COTABLE   {cid, mob 5, type 0, 4096}   ACCEPTED
DXBindShaderIface {cid 1, mob 3, 0x2000}   ACCEPTED
DEFINE_RTV    {rtv 1, sid 3, X8R8G8B8}     ★ STATUS 3 (COMMAND_ERROR) × 4 种路由
```

**卡点**：`DEFINE_RTV`（命令号 1187）在 q0/q1 × dxContext 0/cid 四种组合下全部
COMMAND_ERROR。它**不带 cid**，属于"渲染状态类"命令，必须有"当前上下文"才能解析。

**为什么会缺上下文**：vmwgfx 的正路是 CB header 带
`SVGA_CB_FLAG_DX_CONTEXT` + `header.dxContext = ctx_id`（`vmw_cmdbuf.c:482/1015/1032/1088`）。
而本宿主的 CB header validator **无条件拒绝**除 bit0 以外的任何 flag —— 已用判决实验实锤（§5.1）。
所以这条正路在本机被封死，这是整条链路唯一的死结。

## 4. 难点清单（按"难"排序）

### 4.1 ★★★ CB header 无法表达 dxContext（当前唯一死结）
见 §5.1。不是我们构造错了，是宿主校验器不让。要么找到宿主侧的开关
（能力位/配置项），要么绕开 CB header 表达上下文的机制。

### 4.2 ★★ 宿主是"半实现"的 vGPU10 + 产品级封禁
- 宿主实为 **WS 26.0**（vmware.log 实证），`BaseCapsLevel 9`，MKS 是
  `mksSandbox/ISBRenderer-VK` 新沙箱渲染器。
- 老式 GB 路径（`DEFINE_GB_CONTEXT` + `CLEAR`）被**全量接受但从不渲染**——
  accepted-but-inert，最坑的一种失败形态（fence 全过、状态 MOB 全零）。
- Windows 客体的 vm3dmp 在同一宿主上 3D 正常，这与 flags 被拒的结论冲突，
  是本轮之后要澄清的**头号矛盾**。

### 4.3 ★★ 试错预算极低
- **queue 0 连续失败 4~5 次就楔死**（之后所有 CB status 恒 0、每次等 0.4 s 超时）。
- 设备队列（cbContext **0x3f**）报错**不会**楔死 → 所有试探必须先走 0x3f。
- 每次验证都要 `build → install → reboot`，一轮约 4 分钟；坏 kext 会 panic 循环，
  得靠 VNC 看屏 / vmrun 硬停救。

### 4.4 ★ 逆向对象分散在三个二进制里
| 二进制 | 负责 | 我们已知的锚点 |
|---|---|---|
| `vmware-vmx.exe`（22 MB） | SVGA 设备模型、寄存器、CB 提交与校验、DC 命令、DX 命令分派 | 见 §5.3 |
| `mksSandbox.exe`（3.9 MB） | Vulkan 渲染后端（`ISBRenderer-VK`），经 **replayFifo**（`mksReplay format version=29`）从 VMX 收流 | DX 名字表 `.data 0x36ef50`（idx=cmdId-1040） |
| `vm3dmp.sys`（347 KB） | Windows WDDM 参考驱动（金标准） | 提交 helper `0x1400095d8`、header builder `0x140013990` |

### 4.5 ★ Windows 客体的金标准 trace 还没做
最硬的对证手段：在 Windows VM 里用内核调试器记录 vm3dmp 真实的
`REG_COMMAND_LOW/HIGH` 写入（含 header 字节），与我们逐字节 diff。
一直被"需要内核调试环境"挡着。

## 5. 技术信息库

### 5.1 ★ 判决实验：DX_CONTEXT flag 被 header 层无条件拒绝

校验器 `vmware-vmx.exe!0x140087c10`（.pdata: 0x87c10–0x87cd4）执行顺序：

```
if (header.length == 0) -> COMPLETED            ← 在 flags 检查之前！
page-crossing check on header.ptr.pa + len      -> 失败：status 4
call 0x140607760                                -> 失败：status 4
test dword header.flags, 0xFFFFFFFE             -> 非零：status 4   ★
call 0x140603b30 (命令层)                        -> 命令错误：status 3 + errorOffset
```

利用 `length==0` 的捷径设计实验（kext `kFlagsProbe`，设备队列 0x3f，2026-10-25 00:43）：

| flags | len 0 | len 12（DC cmd1） |
|---|---|---|
| 0 | COMPLETED | COMPLETED |
| 1 | COMPLETED | COMPLETED |
| 2 | **COMPLETED** | **STATUS 4** |
| 3 | **COMPLETED** | **STATUS 4** |

两条结论：
1. flags=2/3 确实走同一个提交函数（len0 的捷径就在同一函数里先返回）。
2. 该函数无条件拒 `flags & 0xFFFFFFFE` ⇒ **CB header 永远无法携带 dxContext**。

### 5.2 DC（设备上下文）命令的真实语义

CB 内设备命令表 @ `0x140A4F6A0`，16 B/条 = `{u32 bodyBytes; u32 pad; u64 handler}`，
推进量 = `4 + bodyBytes`；`id >= 6` 直接走错误路径。

| cmd | body | handler | 语义（实证） |
|---|---|---|---|
| 0 | 0 B | 0x140017ec0 | NOP |
| 1 | 8 B | 0x140087170 | `START_STOP_CONTEXT{enable, context}`，**context 只允许 0**（`cmp [rsp+0x24],0; jne FAIL`） |
| 2 | 8 B | 0x140086e60 | `PREEMPT{context, ignoreIDZero}` |
| 3 | 4 B | 0x140087090 | 上下文槽 idx(0/1)：`word[entry+0xae0]=1` |
| 4 | 4 B | 0x140086c40 | 条件清 `+0xae0` 或置 `+0xae1=1` |
| 5 | 4 B | 0x140086d70 | 清 `qword[+0xad0]`、`dword[+0xad8]` |

- `perVM_ctxBase = 0x141775a60`（`.per_vm` 段，stride 0x118），能力 dword `0x141775b54` = base+0xf4。
- cmd 3/4/5 都先查 **bit29** = 0 就直接失败。
- body 是**上下文索引**，不是 cid（我们一直发 `{3, cid}`，实际含义是"索引 1"）。

### 5.3 ★ per-VM 能力 dword `0x141775b54`

| bit | 含义（推断/实证） |
|---|---|
| 28 | `svga.enableDXContext` 读完立刻检查它（`0x1404bfe58–0x1404bfe6b`）→ DX context 是否可用 |
| 29 | DC cmd 3/4/5 的可用门 |

新主线：这两位由 **power-on 时的 SVGA 能力协商**算出，输入是
`svga.baseCapsLevel` / `svga.capabilitiesMask` / `svga.enableDX*` / guestOS 类型。
候选开关（在 `vmware-vmx.exe` 字符串表里确认存在，都可写进 `.vmx`）：

```
svga.enableDXContext   svga.enableDX / enableDX2 / enableDX3
svga.enableCmdBuffer2  svga.enableRegCommandBuffers
svga.allowHB3DOnPowerOn  svga.allowHB3DOnResume
svga.capabilitiesMask  svga.unsafeFeatures
svga.baseCapsLevel     svga.dump3dCaps / verbose3dCapsLogging
svga.enableCOTableCopy svga.enableHPCmdQueue
```

### 5.4 CB header（`SVGACBHeader`，64 B）

| off | 字段 | 我们的取值 |
|---|---|---|
| 0x00 | status | 0 = NONE，1 = COMPLETED，2 = QUEUE_FULL，3 = COMMAND_ERROR，4 = CB_HEADER_ERROR |
| 0x04 | errorOffset | 出错命令在 payload 里的偏移 |
| 0x08 | id (u64) | 自增 |
| 0x10 | flags | **只能 0 或 1（NO_IRQ）** |
| 0x14 | length | payload 字节数（0 → 直接 COMPLETED） |
| 0x18 | ptr.pa (u64) | payload 物理地址 |
| 0x20 | offset | 0 |
| 0x24 | dxContext | 命令层用；header 校验层不拦（但没 flag 就不生效） |
| 0x28+ | mustBeZero[6] | 0 |

提交：`REG_COMMAND_HIGH(49) = PA>>32`，`REG_COMMAND_LOW(48) = (PA & 0xFFFFFFFF) | (cbContext & 0x3F)`。

### 5.5 结构体尺寸/顺序的坑（血泪）

- `SVGAOTableSurfaceEntry` = **64 B**（不是 72；`surface1Flags` 是 32 位）。
- DXCONTEXT otable 条目 = **8 B**，条目步长表 `0x140a080c0(type)`：type0=16 / type1=64 / type2=8 / type3=16 / type4=64 / **type5=8**。
- `SVGA3dCmdDXSetCOTable` 字段序 = `{cid, mobid, type, validSizeInBytes}`（写成 `{cid,type,mobid,valid}` 会被拒）。
- `SVGA3dCmdDXDefineRenderTargetView` = `{rtvId, sid, format, resourceDimension, desc{mipSlice, firstArraySlice, arraySize}}` = 28 B（已核对，我们的 payload 尺寸是对的）。
- **顺序敏感**：`DXBindShaderIface` 必须在 `SET_COTABLE` **之后**（放前面会让 cotable 被拒）。
