# GPU bundle trust verification

Target: macOS 15.7.3 (24G419), x86_64. Read-only investigation. No settings, authorization, bundle contents, restart, or Git state were changed. 初版未调用私有信任函数；本次追加验证仅以 dlsym 解析并调用两个已核实签名的只读 GPU 查询函数，结果见文末。

## Later verification (2026-11-16, §78–§79)

The observations below describe the earlier read-only investigation. §78 subsequently installed the real VGPUDriverDiagnostic candidate and verified directory/executable trust=0, normal name lookup, and public-CGL-triggered initialize/version/device-rejection/terminate. See out/gld-system-discovery-20261116.txt. This resolves candidate discovery/loading for this guest configuration only; it does not establish default-SIP compatibility or a usable hardware CGL context. §79 corrects the executable-name source to IOGLBundleName based on the loader instructions.

## Conclusion at the earlier investigation

A third-party GLD under `/Library/GPUBundles` is not accepted merely because it is placed there, has ordinary bundle metadata, or is signed. The loader can reach it only if its accelerator supplies a bundle name, the exact `<name>.bundle` directory is found and passes the GPU bundle rootless trust check, and the resulting `Contents/MacOS/<executable>` path also passes that check. The wrappers inspected do not test a signing identity or entitlement directly. Whether a newly created third-party bundle on this target passes the underlying trusted-class check remains unverified; therefore normal third-party loading is possible only conditionally, not demonstrated.

## Verified behavior

1. `gpu_bundle_find_trusted(name, out, capacity)` in target `libsystem_sandbox.dylib` iterates exactly two roots, in order: `/Library/GPUBundles` and `/System/Library/Extensions`. For each it constructs `<root>/<name>.bundle`, calls `stat`, requires the resulting object type to be a directory, and then calls `gpu_bundle_is_path_trusted` on that bundle-directory path. Trust result 0 copies the path and returns success; nonzero advances to the next root; -1 aborts with error. If neither root succeeds it returns 1. Relevant disassembly: `out/sandbox-gpu-code.txt`, `_gpu_bundle_find_trusted` at 0x7FF80E5A7205, especially 0x7FF80E5A727A-0x7FF80E5A7349.

2. `gpu_bundle_is_path_trusted(path)` calls `rootless_check_trusted_class(path, "KernelExtensionManagement")`. If and only if that returns exactly 1, it returns the logical negation of `__dyld_shared_cache_contains_path(path)`; otherwise it returns the rootless result unchanged. Exact acceptance truth table: rootless result 0 passes unchanged; rootless result 1 passes only when __dyld_shared_cache_contains_path(path) is true, because logical negation then yields 0; any other result is propagated. A rootless result of 1 with no cache entry fails (returns 1). The initial prose interpretation had inverted cache membership and omitted the rootless=0 success path; the instruction-level table here supersedes it. This is a storage-class/cache-membership check in the wrapper, not a direct code-signature identity or entitlement check. Disassembly: `out/sandbox-gpu-code.txt` at 0x7FF80E5A73D0-0x7FF80E5A73FD; helper at 0x7FF80E5A73BE-0x7FF80E5A73CB.

3. The caller applies the checks to two distinct paths: first `gpu_bundle_find_trusted` checks the bundle directory; then `libGFXShared` forms `<bundle>/Contents/MacOS/<IOGLBundleName>` and calls `gpu_bundle_is_path_trusted` on that executable path. Only result 0 reaches `dlopen(path, 5)`. Evidence: `out/gfx-loader.txt` at 0x7FFB06174321-0x7FFB06174361 and 0x7FFB0617462B-0x7FFB06174672; `out/gld-loader-contract.txt` lines 17-25.

4. The target rootless policy contains `KernelExtensionManagement /Library/GPUBundles` (read-only guest file `/System/Library/Sandbox/rootless.conf`, line 7); the two GPU search roots are also independently present in the target shared-cache constant table (`out/gld-loader-memory-v3.txt`, lines 781-839). The target `/Library/GPUBundles` currently exists, is empty, and `ls -ldeO@` reports the `restricted` flag; `xattr -px com.apple.rootless /Library/GPUBundles` returns the bytes for `KernelExtensionManagement`. This proves the directory itself is associated with that rootless storage class, not that an arbitrary child bundle/executable inherits or passes the path check.

5. `gpu_bundle_is_path_trusted`'s wrapper has no signing API calls or identity comparisons. The lower-level rootless trusted-class implementation may impose more conditions; its full semantics and the exact metadata/flags a new child requires were not established here. Existing reports' signing queries were inconclusive (`out/gld-bundle-feasibility.txt`, lines 24-29). Do not infer that ad-hoc, self-signed, or any particular Developer ID signature is sufficient or required from this evidence.

## Concrete conditional requirements for `/Library/GPUBundles`

For the observed loader path, all of the following must hold:

- The associated IOAccelerator must publish a nonempty `IOGLBundleName` which reaches `gpu_bundle_find_trusted`.
- The name must resolve to an existing directory exactly at `/Library/GPUBundles/<name>.bundle` (or the second hard-coded root); `find_trusted` does not enumerate arbitrary directory contents.
- `gpu_bundle_is_path_trusted` on that directory must return 0: rootless result 0 is sufficient; alternatively rootless result 1 is accepted only if the path is present in the dyld shared cache. No semantic meaning is assigned to rootless return codes beyond the observed wrapper behavior.
- The observed loader directly uses `IOGLBundleName` for `<name>.bundle/Contents/MacOS/<name>`; the path-building instructions at 0x7FFB06174336..74349 do not read `CFBundleExecutable`. The exact executable must be loadable and `gpu_bundle_is_path_trusted` on it must return 0. Matching plist metadata is conventional packaging, not the source of this observed filename.
- Only after those gates does the caller invoke `dlopen`; normal loading additionally requires the GLD symbols/version contract documented in `out/gld-loader-contract.txt`.

Not established: exact child trusted-class inheritance/attribute requirements; whether rootless accepts the candidate directory and executable on this current custom SIP configuration; whether signing, notarization, team identity, or entitlements affect the lower-level check; and successful normal third-party bundle loading. Those require an authorized controlled test with a real candidate bundle, which was explicitly outside this read-only task.

## 追加验证：真实 rootless 返回码与只读调用（2026-11-16）

保留上述第 2 点和条件列表的已修正逻辑。以下补充底层用户态实现与当前目标实测，不将当前 custom SIP 配置的结果推广至默认配置。

### rootless_check_trusted_class 的真实返回路径

依据同一目标的 `out/sandbox-gpu-code.txt`，Sandbox UUID 再次核对为 `23238A76-3554-3EF9-93A5-D2DE566C6CAC`：

- `0x7FF80E5A73BE–73CB` 将 class 移入第三参数，第二参数置 -1，尾调用 `rootless_check_trusted_internal(path, -1, class)`。路径非 NULL 时，不走 fd 专用分支。
- `0x7FF80E5A6898–68A7` 调用 `csr_check(0x2)`，先将返回寄存器来源 r12d 清零；若 csr_check 返回 0，直接跳到 `69DA` 返回 **0**。这一分支在任何路径/属性查询之前。当前 `csrutil status` 明确显示 Filesystem Protections disabled；本次未直接调用 csr_check，未改变配置。
- 未提前返回时，`68B2–68C7` 调用 `is_path_on_authenticated_root_volume(path)`；该 helper 为真同样返回 **0**。helper 位于 `A6A6–A7C2`，读取 getattrlist；首次读取失败返回 false，后续查询和标志组合决定结果。因此单凭路径前缀不能替代该判断。
- 其余路径在 `6953–69C3` 构造 `__sandbox_ms("Sandbox", 2, &query)` 查询：操作字符串 `file-write-data`，path filter=1，flags=`0x20000005`，class 指针来自调用方。这里只调用查询接口，不写入目标文件。
- `69C8–69D7` 的精确运算：`q = (*reply != 1)`；`neg eax; sbb r12d,r12d` 将 **任意非零 syscall 返回值**折成 -1，零折成 0；最后与 q 做 OR。因此 syscall 非零 => **-1**；syscall=0 且 reply=1 => **0**；syscall=0 且 reply!=1 => **1**。并非将 syscall 的错误码原样当成 rootless 返回码；errno 也不是 rootless 返回值。
- GPU wrapper 随后保持原真值表：rootless=0 => GPU=0；rootless=1 => GPU=!cache_contains；rootless=-1 => GPU=-1。下层内核查询对 storage class 的完整判定与子项继承规则仍未分析完毕。

### 实际构建与运行

新增 `kexts/probes/gld_trust_probe.c`，未修改 `gld_loader_probe.c`。探针通过 `dlsym(RTLD_DEFAULT, ...)` 解析真实符号，并用 `dladdr` 确认函数名称和 `/usr/lib/system/libsystem_sandbox.dylib` 来源；签名分别为 `int(const char *)` 和 `int(const char *, char *, size_t)`。没有 dlopen、bundle 加载、属性写入、安全设置更改或权限更改。
