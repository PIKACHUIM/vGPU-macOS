GLD 最小 context / clear / readback 契约：硬件交叉核验
日期：2026-11-16
目标：macOS 15.7.3 / 24G419；x86_64 / x86_64h；静态研究交付。

0. 结论及实现边界
已闭合 share -> context 六参 -> A/H/B 借用状态 -> FBO Q/D -> 当前 read handle -> pack 的关键链条。可以据此编写独立句柄生命周期与稀疏视图适配层；尚不足以宣称真实 GPU clear/readback 已可运行。
本轮未调用 GLD 私有入口，未执行 GPU 提交、安装、重启，未修改内核、驱动代码、其他代理文件或已有研究文档。客体仅执行只读反汇编/检索和保存独立证据；宿主仅新增本报告及 gld-context-* 原始文本。没有运行绘制探针。
关键修正：所查 Intel KBL/ICL、AMD X4000/X5000 的初始 Populate 全部将 render[0] 清零。KBL、X4000、X5000 的配置已实证 A+0x6e=1，采用显式三参 ClearFramebufferData；不能称 render[0] 为这些硬件已验证可用的 clear 路径。ICL本轮只检查 Populate，未独立闭合其配置。
25槽的清单完整，签名恢复不完整：0/2/20/21/24具有较强调用形态证据；1有AMD实现及内部调用证据；3..12、17..19主要是GLEngine调用现场；13..16无可确认参数。缺失处明列为阻塞，不用统一无参/固定成功桩补齐。

2. 可落实到独立入口的 ABI
以下声明是本目标寄存器宽度的适配表示，不是Apple私有头文件；opaque参数不因写成void*就得到完整对象定义。

 int32_t gldCreateShareGroup(void *Dev, void **out_SG, uintptr_t opaque_arg3);
 int32_t gldCreateContext(void *SG, void **out_C, void *pixel_format,
                          void *A, void *H, void *B);
 int32_t gldDestroyContext(void *C);
 int32_t gldDestroyShareGroup(void *SG);
 Populate调用形态：gldPopulateContextDispatch(C, R_storage_25_pointers)。源语言返回类型未恢复。

2.1 Share
libGFXShared 0x7FFB06174A0F/4A19/4A1D/4A22：RSI=share输出槽、RDI=Dev、EDX=4，调用plugin+0x478(T+0x58)。因此本调用的RDX完整值为4。
Mercury 0x7FF9183586CA保存完整RDX，0x7FF91835871E写SG+0x10；不能仅因调用者写EDX就把所有调用的第三参数定为uint32 flags，更不能称为指针。uintptr_t只用于保留实际机器值，正式语义和通用宽度契约未恢复。
Create入口清*out_SG；调用IOAccelSharedCreate、按库配置大小分配SG、初始化锁/processor、调用Dev+0x10初始化回调；成功0x7FF918358789写输出并EAX=0。可见失败值0x271f/0x2724，不据此命名所有错误。
Destroy由plugin+0x480(T+0x60)调用，首参SG。Mercury清共享纹理、调用Dev+0x18、释放IOAccelShared/processor/锁/SG，0x7FF918358823 EAX=0。
独立实现自己拥有SG及资源，不得free Dev或调用者输出槽。共享资源和context引用必须在销毁前解除；完整并发/引用计数约定仍需补证。

2.2 Context
GLEngine 0x7FFB0637B27A调用plugin+0x488(T+0x68)：RDI=SG、RSI=S_i、RDX=pixel_format、RCX=A、R8=H、R9=B，EAX=0继续，否则走清理。
Mercury入口0x7FF9183542C8保存六参并清*out_C。pixel_format先由Dev+0xf8校验，并检查pixel_format+0x34 mask属于Dev+0x23c。
0x7FF9183545BC保存SG；45C7保存H；45D2保存B；478C调用Dev+0x100(C,A,pixel_format)填配置；4794保存A；479F写*out_C；47A2 EAX=0。
Mercury自身布局：C+8=Dev，+0x10=SG，+0x18=H，+0x20=A，+0x28=B，+0x30=current_draw，+0x38=current_read，+0x40=IOAccelGLContext。
此布局仅解释硬件证据。独立GLD可自行定义C，不必按这些偏移分配；一旦借用Mercury函数则不能省略其内部依赖。
特别注意：Mercury Create自身调用IOAccelGLContextCreate/GetSidebandBuffer/GetFenceBuffer，0x7FF9183544DD调用gpusSubmitDataBuffers。它不是可在“禁止GPU提交”范围内安全试调的纯分配探针。
A/H/B是调用者持有且后续会改变的借用视图。保存指针，不拷贝猜测大小的整个对象，不在create时永久缓存pack/FBO状态。
GLEngine失败清理0x7FFB0637B4FE向plugin+0x498(T+0x78)传单参C。Mercury Destroy入口0x7FF9183549F7解除program关联、释放drawable、调用Dev+0x28、释放processor/IOAccelGLContext/私有内存；4AE3 EAX=0。
上述Destroy使用int32返回是符合已查callee的可实现适配形态，不是由调用者未检查返回推导正式源语言类型。

2.3 Populate
GLEngine 0x7FFB06447500以RDI=C、RSI=G+0xb320调用T+0x88；不检查返回；随后gleUpdateDispatchJIT复制25指针。
Intel KBL 0x7FFB020B40EB..4148将0..19、22..23清零，20=glrIntelBeginPrimitiveBuffer、21=glrIntelEndPrimitiveBuffer、24=glrIntelNoopRenderVertexArray。
AMD X5000 0x630F8..631A2保存R到C+0x80；0=NULL、1=glrdATI_Hwl_DrawPixels、2=glrdATICopyPixels、20/21=Begin/EndPrimitiveBuffer、22/23=NULL、24=glrdAMD_RenderVertexArray；3..12、17..19初始指向glrAMD_GFX9_NoOp；13..16=NULL。
X4000/ICL的初始槽0同样NULL。初始NULL/NoOp不证明执行任意API都安全，UpdateDispatch/能力/回退条件仍需要满足。
GLEngine在fallback begin/end及gliUpdateDispatchState会重新Populate；不能把一次填表当整个生命周期不变。

4. clear：实际硬件选择与数据契约
4.1 A的写入责任
Mercury通过Dev+0x100(C,A,pixel_format)调用配置填充。
Intel glrPopulateContextConfig尾跳IntelSetConfigData，RSI=A。
0x7FFB020B3E05 movl $0x1000001,0x6b(%rbx)：小端字节01 00 00 01，明确A+0x6e=1；+0x6f另外写1。
机器字节0x7FFB020B3E03起含 C7 43 6B 01 00 00 01；已独立section_bytes确认。
AMD X4000 0x575A0、X5000 0x1364C将word 0x101写A+0x6d，明确A+0x6e=1。
这不是扩展名字推导；同一字节被GLEngine实际分支读取。

4.2 A+0x6e==0
GLEngine 0x7FFB0639792F检查A+0x6e；到0x7FFB063979C9以(C,过滤后的GL mask)调用R[0]。
颜色0x4000、深度0x100、stencil0x400依据G+0x458e/+0x458f有效性过滤；没有清除值参数。
clear setter可置dirty 0x8/0x10/0x20。上层可定位H+0x3bf0的16字节颜色、H+0x3bd8的double depth、H+0x3c04的stencil容器，但本轮没有硬件R[0]callee证明如何消费这些值。
因此只验证了调用形态，不能将此分支当最少已验证硬件实现方案。

4.3 A+0x6e!=0
GLEngine 0x7FFB06397A42调用T+0xd0：gldClearFramebufferData(C,u32 internal_mask,void *clear_values_inout)。
internal_mask不是GL mask：低8位是所选颜色目标位，bit8 depth，bit9 stencil；不能把低8位解释为RGBA通道掩码。
数据块V至少覆盖0x1c字节：
 V+0x00 16字节颜色；普通glClearColor为四float，整数Clear路径可用原始整数编码。
 V+0x10 4字节float depth（上层double转换）。
 V+0x14 4字节stencil容器。
 V+0x18 4字节，此glClear路径写0，完整语义未恢复。
未选字段由上层清零；V是栈临时内存，不能保留到返回后。
Intel导出offset0x35ad，function_starts确认入口0x7FFB01EBD5AD、下一入口0x7FFB01EC060E；入口字节55 48 89 E5，线性输出从+1开始不是ABI异常。
0x7FFB01EBD64F保存RDX=V，0x7FFB01EBDAFD读V+0x10，0x7FFB01EBDB17回写V+0x10。故V不能声明为const。
Intel还读取当前draw framebuffer C+0x30、H+0x3d84及硬件资源/管线状态；显式传颜色不意味着只写四字节就完成clear。scissor、color write mask、附件格式/sRGB等完整消费尚未收敛。
该函数返回类型/所有返回路径本轮未恢复；GLEngine上述调用不检查返回。

5. Q/D/FBO 的硬件闭合关系
P=framebuffer数据基址；命名FBO的P=F+0x28。
Q=P+0x100；D_i=P+0x200+0x58*i；O_i=P+0xa0+8*i。
GLEngine 0x7FFB06454F93 / 0x7FFB06454B11调用CreateFramebuffer(SG,O_i,Q,D_i)。
可实现形态：int32_t gldCreateFramebuffer(void *SG, void **out_fb, void *Q, void *D)。
Mercury 0x7FF918355FB7保存Q到fb+0；5FBA保存D到fb+8；5FD2写*out；5FD5 EAX=0。
独立句柄布局可自定；Q、D均借用，不能释放或将D[0]当Q。
D+8*j(j=0..9)是对应插件附件纹理句柄；GLEngine 0x7FFB06455914/55919为实际生产者。
Q+0xb2/+0xb4是uint16宽高；命名FBO对应F+0x1da/+0x1dc。实际完整性生产者以P为基址写P+0x1b2/+0x1b4；不能只靠偏移算术推断。
Q+0xc0为Mercury Load迭代的附件位图；Q完整格式/层/采样布局未恢复。
Mercury Load(SG,fb)：先D+0x51=1，按Q+0xc0取D附件加载，再调用Dev+0x108；收尾sete D+0x51，清D+0x50，EAX=(D+0x51==0)。若前面附件加载失败可提前退出，不能把所有路径说成总会清pending。
GLEngine实际以D+0x50决定是否Load，以D+0x51 bit0判定失败，并不依赖本调用EAX。固定返回1不能替代状态/资源协议。
UpdateDraw(C,u32 dirty)在bit30时读取B+0x4a0；UpdateRead(C,u32 dirty)在bit31时读取B+0x4a8。第二参数是dirty，不是fb句柄。
Mercury read写C+0x38，draw写C+0x30；bind回调为Dev+0x168/+0x160；draw状态更新回调为Dev+0x148。
Mercury UpdateRead返回1；UpdateDraw依据C+0x944返回1或2。不同入口不能套用“统一0成功”。
附件纹理自身backing/pitch/格式与资源同步仍是必要阻塞；创建一个保存Q/D的包装不是资源已可用。

6. ReadFramebuffer：十参及pack
寄存器/栈载体适配形态：
 int32_t gldReadFramebufferData(void *C, int32_t x, int32_t y,
   int32_t width, int32_t height, uint32_t format, uint32_t type,
   void *pixels, uint32_t mode32, void *buffer_handle);
返回类型int32只表示实际EAX分支载体；PBO路径的非0不是简单错误码。
标准x86_64帧下第7..10参数在rbp+0x10/+0x18/+0x20/+0x28。
GLEngine CPU分支0x7FFB063B6B02传mode32=0、buffer_handle=NULL；x/y/w/h已被裁剪，pixels已包含上层裁剪导致的地址修正。
Mercury wrapper 0x7FF918358254在buffer非NULL时检查/加载驱动buffer，随后尾跳Dev+0x1b0，保留十参栈布局。
Intel 0x7FFB01EDE200以movl读mode32，DE204以movq读pixels，DE208以movl读type；DE210从C+0x38取fb；DE225取Q=*fb；DE228/DE232读uint16宽高。
默认fb为NULL时读取Intel私有C+0x120c/+0x1210；不能用这两个偏移替代独立驱动drawable契约。
H=*(C+0x18)，pack=H+0x4ec8（DE258）；mode32==2时将pack置NULL（DE261/DE265）。AMD CopyPixels内部也用mode=2调用read，这交叉支持该模式绕开普通pack，并未恢复其全部语义。
Intel调用gpusPixelSettings时的pack是第8参数；不要与Float同名辅助函数的第9参数混用。辅助函数并非GLD导出ABI。
已证pack稀疏视图：
 +0x00 u32 row_length
 +0x04 u32 current_row_stride_bytes
 +0x10 u32 skip_rows
 +0x14 u32 skip_pixels
 +0x1c u32 alignment
 H+0x4ee8/+0x4ee9为swap-bytes/lsb-first，Intel分别读取；最小RGBA8路径仍不能缓存旧状态。
gpusPixelSettings 0x7FF918357232先取pack+4，非0直接用；否则取row_length或width并按alignment向上取整；3572A0/2C2按skip_pixels/skip_rows计算目标偏移。
仅限普通2D RGBA/UNSIGNED_BYTE、非bitmap模式的可独立实现公式：
 row_bytes = current_stride != 0 ? current_stride : align_up((row_length > 0 ? row_length : width)*4, alignment)
 pack_offset = skip_rows*row_bytes + skip_pixels*4
 row_destination(j) = pixels + pack_offset + j*row_bytes
不能再次重复加入上层已经计入pixels的裁剪offset。实现时用经检查的宽整数运算，保证目标内存容量；不要照搬原驱动32位乘法的溢出行为。
GLEngine会在read调用前临时写H+0x4ecc，返回后恢复；必须每次读取当前pack。
PBO路径、mode其他值、bitmap/整数/深度/多采样/IOSurface均不在该最小公式范围内。

12.1 H默认状态晚于驱动CreateContext
GLEngine先在0x7FFB0637B27A调用驱动CreateContext，再在B4CE调用gleInitializeContext；后者C4FF将G+0x8e0作为首参，在C51E调用gleInitGLDState。
因此H内容在驱动Create返回后仍被上层初始化。Create中保存H指针即可；不能把当时的clear/pack值永久缓存成运行时状态。
function_starts确认gleInitConstants范围[C9DC,CD18)，gleInitGLDState范围[CD18,D6DB)，gleInitGLIState范围[D703,DA69)，上述低地址均加0x7FFB06370000。
线性反汇编漏掉GLD/GLI入口标签，并在入口前后出现跨界误解码；init-consumers原始文件中“gleInitConstants”标签后包含相邻GLD函数，不能把整段都归属Constants。实际归属由init-dispatch-bounded文件的function_starts边界限定，入口附近缺失指令不用于参数推导。
在已限定GLD函数内，RBX=H：
 0x7FFB0637CE39 写H+0x3bf0的16字节颜色为0。
 0x7FFB0637CE51 写H+0x3bd8为double 1.0。
 0x7FFB0637CE5B 清H+0x3c00..07，覆盖stencil容器H+0x3c04。
 0x7FFB0637CF20/CF27 清pack+0..0x1b；CF2E写pack+0x1c=4。
 0x7FFB0637CF38 清H+0x4ee8起的swap/lsb相关字节。
这些默认值与已验证硬件read消费者闭合；不表示驱动应自行覆盖上层当前状态。

12.3 AMD动态描述符链及槽20的实质修正
GFX9_UpdatePrimitiveBufferState 0x4E529/4E564从C+0x20取A，RDX=C+0x2bb8，调用glrATI_UpdatePrimitiveBufferState；后者0x21920把*(C+0x2bb8)写A+0x208。
当内部源对象及其+0x300字段允许时，0x21E42将另一描述符写A+0x210；否则0x21DA9清A+0x210。描述符+0x02由该生产者写入步长相关值，GLEngine随后还会将零值改成1。
这闭合了“硬件填指针 -> 上层读取/调整描述符 -> 硬件Begin消费”的双向共享关系；A不是create后只读快照。此更新函数操作的是描述符，不等于安装render[13..16]或[22..23]，没有得到这些槽的新ABI证据。
AMD BeginPrimitiveBuffer的实际入口由function_starts确认是0x21EA4，下一入口0x22030；之前标签提取漏掉它。
关键数据流：
 0x21EAF 保存RDX；0x21EBC先读*(uint32_t*)RDX。
 若该输入非0且A+0x210非NULL，选第二描述符；否则0x21EDD选A+0x208。
 0x21F08读取所选描述符+2；0x21FFD将其作为32位除数。
 0x22022写回32位值；0x22024以RAX返回缓冲指针。
所以槽20第三参必须按“输入选择值/输出容量共用的uint32_t指针”处理，不能标为纯out或传未初始化存储。GLEngine已见现场0x7FFB0639B089在调用前写0，支持这一修正。
可适配声明仍为 pointer render20(C,u32,uint32_t *count_inout)，但输入完整语义/第二参数正式名称尚未恢复；AMD本实现没有消费原始ESI，不据此删除该调用者形参。
所选描述符必须存在且+2非零才满足这个AMD路径的解引用/除法前置；初始A+0x208/+0x210都NULL不能直接进入Begin。这是具体硬件路径前置，不把AMD私有资源布局强加给独立驱动。
